## Governance-iteration friction (2026-08-09 P109 AFK iter)

- **A `blob/master` link in outbound prose resolves against the REMOTE, so it 404s for every reader while your commits are unpushed.** The P109 upstream lifecycle comment passed both the external-comms risk gate and the voice-tone gate, and the risk gate then caught this separately because it had been asked to verify the draft's claims against disk: local `master` was ahead of `origin/master`, and the commit creating the linked path was in the unpushed set. Nothing in the prose was wrong; the link was simply unreachable. If an AFK iteration is barred from pushing, an outbound comment that deep-links a just-written path cannot be posted in that iteration -- queue it, do not reword it, because risk-reducing the prose cannot fix an unresolvable link. Prefer linking a path that already exists on the remote, or defer the post until after the push.

- **When a rule keys on a coarse unit, it silently discards good input, and both governance gates will catch that before you do.** P109's first draft said "if an external review round comes back stale, discard it and re-run". The architect and the JTBD reviewer independently returned ISSUES FOUND on the same defect: a partly-stale round is the normal shape, so discarding the round drops findings still true of the current text. The fix was to triage per finding and require staleness to be affirmatively demonstrated. Worth generalising: when writing a rule that discards something, check the granularity of the thing being discarded and fix the failure direction explicitly. This repo has already ratified that direction twice, in ADR-046 ("When in doubt, re-run") and ADR-047 ("toward a wasted invocation, never toward a silent miss"), so cite those rather than re-deriving the argument.

- **Two adjacent tickets can share an event and still be separate defects; the test is a counterfactual, not a similarity judgement.** P099 (stale gate verdicts) and P109 (a stale reviewer copy) were both generated by Issue 16's six post-ledger external review rounds, which makes them read as one defect in the retro. The question that separates them: had the other ticket's fix been in force at the time, would this failure still have happened? ADR-047's digest mechanism cannot see what is handed to a person outside the repo, so yes -- the reviewer would still have read stale text. Run that counterfactual before folding one ticket into another, and record the argument on the ticket rather than just the conclusion.
