- **The Bash tool runs zsh, so bash-only array syntax fails with "bad substitution".** A scripted batch operation (the 2026-06-28 verification-queue drain) used a bash associative array with `declare -A` and `${!EV[@]}` inline in a Bash tool call; zsh rejected `${!EV[@]}` with `(eval):N: bad substitution` and nothing ran (which is the safe outcome: an aborted compound command leaves no partial state). For any non-trivial script using bash arrays, `${!arr[@]}`, `${arr[@]}` expansions, or other bashisms, write it to a file (e.g. `/tmp/foo.sh` with a `#!/usr/bin/env bash` shebang) and run it with `bash /tmp/foo.sh`, OR use zsh-native syntax (`typeset -A`, `${(k)arr}`). - **A stray `.env` FIFO makes `next build` (and `next dev`) hang forever at 0% CPU.** P001 (open since April, "build hangs locally") was root-caused 2026-06-27 to `./.env` being a named pipe (FIFO, `prw-------`), not a regular file. Next loads `.env` files at the very start of the build; opening a FIFO read-only blocks indefinitely under POSIX (it waits for a writer that never comes), so the build hangs right after the prebuild step with no output and no CPU use. Diagnosis path that works: `sample <pid>` the stuck `node .bin/next build` process (it shows a blocked `open()` / `uv_fs_open` syscall), then `ls -la .env` (look for the `p` FIFO prefix) or `find . -type p`. The earlier 2026-05-30 "unreproducible" note checked process state rather than the `.env` file type, which is why it missed the cause for two months.

- **A plain `mv` onto an existing directory does not refuse, and a scoped `git add -A` after a move aborts on a never-tracked source.** Both surfaced fixing P118 and both exit in ways that read like success or like an ordinary error. `mv a/<date>/ b/<date>/` where `b/<date>/` exists nests to `b/<date>/<date>/` and exits 0, so a publish step reports success while the edition falls out of the one-level-deep edition-count glob. And `git add -A <src> <dst>` after the move exits 128 with `fatal: pathspec ... did not match any files` when the source was never tracked, because the pathspec matches nothing in worktree or index; both pathspecs share one invocation, so the whole command fails after `mv` already landed, leaving the edition promoted with nothing staged. Staging the source BEFORE the move fixes it. The general lesson: reach for `test ! -e <dest>` before any scripted directory move, and reproduce each branch in a scratch repo rather than reasoning about git's pathspec rules.

- **The session-start `git status` snapshot strips the leading space from the FIRST line only, so line 1 reads as a staged file when it is not.** Porcelain uses two columns, index then worktree, so an unstaged modification is ` M path` with a leading space. In the snapshot handed to a session the first entry loses that space and renders as `M path`, which is the staged form. On 2026-08-09 the risk scorer read `M output/pdf/paper.pdf` off that snapshot, concluded Tom's in-flight paper was staged, and returned STOP on a precondition that was never breached; the file had never been staged and nothing needed unstaging. - **The external-comms gate cannot see a body passed with `--body-file`, and the block it emits is then unclearable.** The PreToolUse gate scrapes the draft out of the command string itself, matching a heredoc, then `--body "..."`, then `-m "..."`. With `--body-file /tmp/x.md` nothing matches, so it hashes an EMPTY draft: `sha256("" + "\n" + surface)`. The reviewer subagent hashes the real body from its `<draft>` block, the two keys never meet, and the gate re-blocks after a genuine PASS with the same message telling you to do the review you just did. Nothing in the message hints at the cause. The fix is to pass the body inline as `--body "$(cat <<'EOF' ... EOF)"`, which the gate parses first and by design. Two other traps sit next to this one: the reviewer must be dispatched SYNCHRONOUSLY (a background agent never fires its PostToolUse mark hook), and its prompt must literally start with a `SURFACE: <name>` line and wrap the body in `<draft>...</draft>` markers, or the key is never derived at all. A review run without that shape is wasted work, however good the review is. Observed 2026-08-08 filing agent-plugins#413.

- **The commit-message external-comms gate is a DIFFERENT trap from the `--body-file` one above, and the recipe lives in the plugin's briefing, not this repo's.** The gate parses the raw command string with a first-match-wins loop over `-m` and captures only the FIRST one, while the reviewer subagent hashes whatever you wrapped in `<draft>`. Three recipes work: a single `-m` inlining the whole message reviewed as full text; a multi-`-m` commit reviewed as the SUBJECT LINE ONLY; or `git commit -F <file>`, which sidesteps the gate entirely because it arms only on `-m`/`--message`.
