## Verification discipline

Checks that are wrong in the same direction as the work they check. This file exists because 2026-08-09 to 2026-08-10 produced five instances in one session, and the failure mode is not carelessness: each check was written immediately after the thing it verified, by the same reasoning, so it inherited the same assumption.
- **`wr-itil-reconcile-readme` exiting 0 does not mean the problems README is accurate.** On 2026-08-23, immediately after `git mv`-ing a ticket from `open/` to `known-error/`, the preflight returned exit 0 (clean) while the README's row for that ticket still read `Open`. The script reconciles the *inventory* (which IDs appear in which section) and does not read the Status column inside a row, so a status that moved without its row being rewritten is invisible to it. The P062 refresh-on-transition contract is what actually owns that edit, and it is the agent's job, not the script's. Treat the green exit as "no tickets are missing", never as "the README is right", and read the row you just changed.

- **A ticket's close criterion can be quietly superseded by a decision ratified after it was written.** P120's criterion, written 2026-08-05, said the fix is not working "if the loop runs more than one round per body pass". ADR-052, ratified five days later, made every newsletter reviewer gate blocking, so a surviving finding now holds the edition and each fix starts a further body pass. A verification note read a 24-round finalise against that criterion, called it a regression by a factor of twenty-four, and the ticket was flipped back to Known Error on Tom's confirmation of that reading. The twenty-four counted body passes; the criterion caps rounds inside one. Check what has been ratified since a criterion was written, and that the evidence counts what the criterion counts. Corrected on P120 and P113.

- **A reviewer telling you how much it read is not evidence that it read that much, and the number is the thing to check.** On 2026-08-29/30, during the P120 close, a scoring pass wrote "I read all 549 lines of" a reviews file and concluded a quoted sentence was absent from it, raising a remediation to rewrite the citation. The file is 616 lines and the sentence is at 611. Two more absence claims in the same finding were false the same way. The next pass, asked to check the line count, refuted its predecessor. What makes this worse than an unsupported claim is that the stated extent reads as the verification already done, so the standing verify-before-propagating discipline passes over it: there is no missing artefact to catch and no fabricated reference. `wc -l` against whatever extent a verdict names costs one command, and an absence claim that names no extent has not established anything. Applies to any reviewer, including the ones whose findings are usually right -- the same four-pass sequence that produced this one raised twelve remediations, of which nine were genuine defects that were applied. Ticketed as P178.
