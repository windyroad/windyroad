## Governance surface conflicts

Cases where two governance surfaces hold different beliefs about the same thing and nothing reconciles them. Several surfaced in a single session on 2026-08-09, which is why this has its own file rather than a bullet elsewhere; the GitHub Actions pinning entries split out to their own topic on 2026-08-29. The shared shape: each surface is individually correct, both are ratified or shipped, and the disagreement is invisible until something sits exactly on the seam.

- **The RFC lifecycle cannot advance past `proposed` in this repo, and never has.** `/wr-itil:manage-rfc <RFC> accepted` hard-blocks on `wr-itil-check-rfc-has-stories`, which fails any RFC with an empty `stories:` array per upstream ADR-089. ADR-045 here is `human-oversight: confirmed` and says RFCs carry `stories: []` until a story tier exists, which it does not (`docs/stories/` and `docs/story-maps/` are both absent). The gate cannot read ADR-045, and ADR-045's Scope paragraph enumerates what it does not touch without naming the gate. Verified total, not per-RFC: the gate returns exit 1 for all six RFCs on disk and none has ever reached `accepted`. **What to do instead:** record the ratification on the `human-oversight` axis, which ADR-049 establishes as separable from lifecycle `status` (it carries `status: "proposed"` with `human-oversight: confirmed` itself). Know what that skips: the `## Commits` render, the reverse trace onto the driving problem, and the README ranking, whose WSJF status multiplier is 1.0 at proposed against 2.0 at accepted. The ranking depression is uniform across all six, so relative order still holds. Ticketed as P142.

  **The same absent tier now blocks most fix work outright, which is the bigger half and was not visible on 2026-08-09.** Confirmed 2026-08-29 while working P128: `manage-problem`'s I13 propose-fix trace gate runs on every Known Error *before* any fix is implemented. `wr-itil-check-fix-rfc-trace` answers from the union of two tiers, and the order matters. A legacy RFC document whose frontmatter `problems:` array names the ticket short-circuits to exit **0**, and the story-map branch runs only after that misses, exiting **3** because the repository holds no story maps at all. A fix proposal is now a release row on a story map, never a document, and drawing the first map for a journey decides what that journey is, so the gate refuses to create one and routes the item to a person. The skill's instruction on that branch is explicit: record one item for the maintainer and carry on to the next problem, do not stop the loop. **So an untraced Known Error cannot have a fix implemented through `manage-problem`, AFK or attended, until somebody draws the first map.** Measured across all 29 known errors on 2026-08-29: 27 exit 3, and only P099 and P120 clear the gate, through RFC-005 and RFC-002 respectively. An earlier draft of this paragraph said *no* Known Error could be fixed, which the risk scorer caught by reading the predicate rather than the prose; the document tier is easy to miss because the story-map branch is the one that prints an explanation. Reaching the gate costs almost nothing, so run the predicate rather than pre-screening or assuming which kind of ticket you have.

- **The newsletter structure lint and the `wr-newsletter` SKILL disagree on where the prep reviews sibling lives, so one of them is always wrong during prep.** The lint derives it mechanically as `${brief%.md}.reviews.md`, which during prep resolves to `<date>.prep.reviews.md`; SKILL step 16 prescribes `<date>.reviews.md` and step 0.5 binds that name to read prep verdicts forward at finalise. The names agree only at finalise, when the brief loses its `.prep` infix, which is why sixteen published editions never exposed it. Satisfying the lint loses the prep residuals at the phase boundary; satisfying the SKILL means the ADR-047 scored-digest staleness check never runs during prep at all, for any edition. Issue 17 took the SKILL side, because the carry-forward is functional and the lint degrades to a loud SKIP. Ticketed as P140.
