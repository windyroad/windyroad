## Governance surface conflicts

Cases where two governance surfaces hold different beliefs about the same thing and nothing reconciles them. Three surfaced in a single session on 2026-08-09, which is why this has its own file rather than a bullet elsewhere. The shared shape: each surface is individually correct, both are ratified or shipped, and the disagreement is invisible until something sits exactly on the seam.

- **The RFC lifecycle cannot advance past `proposed` in this repo, and never has.** `/wr-itil:manage-rfc <RFC> accepted` hard-blocks on `wr-itil-check-rfc-has-stories`, which fails any RFC with an empty `stories:` array per upstream ADR-089. ADR-045 here is `human-oversight: confirmed` and says RFCs carry `stories: []` until a story tier exists, which it does not (`docs/stories/` and `docs/story-maps/` are both absent). The gate cannot read ADR-045, and ADR-045's Scope paragraph enumerates what it does not touch without naming the gate. Verified total, not per-RFC: the gate returns exit 1 for all six RFCs on disk and none has ever reached `accepted`. **What to do instead:** record the ratification on the `human-oversight` axis, which ADR-049 establishes as separable from lifecycle `status` (it carries `status: "proposed"` with `human-oversight: confirmed` itself). Know what that skips: the `## Commits` render, the reverse trace onto the driving problem, and the README ranking, whose WSJF status multiplier is 1.0 at proposed against 2.0 at accepted. The ranking depression is uniform across all six, so relative order still holds. Ticketed as P142.

- **The newsletter structure lint and the `wr-newsletter` SKILL disagree on where the prep reviews sibling lives, so one of them is always wrong during prep.** The lint derives it mechanically as `${brief%.md}.reviews.md`, which during prep resolves to `<date>.prep.reviews.md`; SKILL step 16 prescribes `<date>.reviews.md` and step 0.5 binds that name to read prep verdicts forward at finalise. The names agree only at finalise, when the brief loses its `.prep` infix, which is why sixteen published editions never exposed it. Satisfying the lint loses the prep residuals at the phase boundary; satisfying the SKILL means the ADR-047 scored-digest staleness check never runs during prep at all, for any edition. Issue 17 took the SKILL side, because the carry-forward is functional and the lint degrades to a loud SKIP. Ticketed as P140.

- **GitHub Actions versions have no detector here at all.** No `dependabot.yml`, no `renovate.json`, and `npm run deps:check` is scoped to root npm manifests per ADR-021 and ADR-034, so it structurally cannot see Actions refs. Demonstrated cost: `changesets/action` sat pinned fifteen months and surfaced only when GitHub emitted a Node 20 deprecation annotation. An external deprecation notice was the only detector. The sharpest instance is `trufflesecurity/trufflehog@main`, a moving-branch third-party pin running in the first job after a `fetch-depth: 0` checkout with no top-level `permissions:` block, where the executed code can change between two runs with no diff here. Ticketed as P141.

- **Pin the commit SHA, not the annotated tag object.** Both resolve in Actions, so the difference is invisible until you try to audit one. `gh api repos/<o>/<r>/commits/<sha>` returns 422 on a tag-object SHA, and Dependabot's action updater and most pinning auditors expect the commit form. `git ls-remote` is what resolves the mystery: it prints the tag object against `refs/tags/vN`. Worth checking when a pin will not resolve and looks corrupt.

- **When bumping a pinned action, verify its `outputs:` block at the new ref, not just `runs.using`.** A dropped output does not fail; the step that consumes it silently skips on a green job. On 2026-08-09 the risk scorer caught this gap on the `changesets/action` bump: `pullRequestNumber` gates two steps in the only path to production, and a green CI run cannot distinguish "output works" from "output dropped" when no changeset is queued, because the output is legitimately empty either way. Diff the block at both refs before and after.
