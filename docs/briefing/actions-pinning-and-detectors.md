## Pinning and detecting GitHub Actions

> Split out of [`governance-surface-conflicts.md`](governance-surface-conflicts.md) on 2026-08-29 (Tier 3 budget rotation, split-by-subtopic: that file went over the 5120-byte ceiling and these three entries form a self-contained sub-topic over 1 KB).

- **GitHub Actions versions have no detector here at all.** No `dependabot.yml`, no `renovate.json`, and `npm run deps:check` is scoped to root npm manifests per ADR-021 and ADR-034, so it structurally cannot see Actions refs. Demonstrated cost: `changesets/action` sat pinned fifteen months and surfaced only when GitHub emitted a Node 20 deprecation annotation. An external deprecation notice was the only detector. The sharpest instance is `trufflesecurity/trufflehog@main`, a moving-branch third-party pin running in the first job after a `fetch-depth: 0` checkout with no top-level `permissions:` block, where the executed code can change between two runs with no diff here. Ticketed as P141.

- **Pin the commit SHA, not the annotated tag object.** Both resolve in Actions, so the difference is invisible until you try to audit one. `gh api repos/<o>/<r>/commits/<sha>` returns 422 on a tag-object SHA, and Dependabot's action updater and most pinning auditors expect the commit form. `git ls-remote` is what resolves the mystery: it prints the tag object against `refs/tags/vN`. Worth checking when a pin will not resolve and looks corrupt.

- **When bumping a pinned action, verify its `outputs:` block at the new ref, not just `runs.using`.** A dropped output does not fail; the step that consumes it silently skips on a green job. On 2026-08-09 the risk scorer caught this gap on the `changesets/action` bump: `pullRequestNumber` gates two steps in the only path to production, and a green CI run cannot distinguish "output works" from "output dropped" when no changeset is queued, because the output is legitimately empty either way. Diff the block at both refs before and after.
