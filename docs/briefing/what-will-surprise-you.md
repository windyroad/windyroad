- **Every governance marker in this stack is written by a `PostToolUse` hook whose matcher is the literal string `Agent`, so anything that is not a fresh synchronous `Agent` spawn marks nothing.** Six hooks, one shape: architect, jtbd, risk-score, voice-tone, external-comms and style-guide. A `SendMessage` resume fires none of them, and neither does a background-launched reviewer. Only `wr-architect` documents this, in one deny string (`hooks/lib/architect-gate.sh:64`, the P400 note); the external-comms gate documents the background half only (`external-comms-gate.sh:413`, P402). The other four say nothing, so the block arrives with no way to work out why. Two corollaries worth holding. Widening the matcher would not fix it as the hooks are written, because they identify the reviewer from `tool_input.subagent_type` and a `SendMessage` payload has no such field. And on `wr-architect` 0.20.0, which is what this repo runs, verdict FORMATTING is not a cause: the mark hook routes an unparseable verdict into the same allow-with-marker branch as PASS, so a block after a genuine PASS means the marker landed under a session ID nobody reads (P088), not that the heading was the wrong shape. Recorded on P124. **The uniformity is version-pinned and is already breaking upstream**: `wr-risk-scorer` 0.18.6, sitting in the cache for another project, has collapsed its four hooks into one dispatcher whose `PostToolUse` matcher is `Agent|Bash|Edit|Skill|Write|` plus eleven agent-lifecycle events (`spawn_agent`, `wait_agent`, `close_agent` and their `multi_agent_v1__` forms). Two things follow. Re-read the hooks after any plugin upgrade rather than trusting this entry. And there is upstream precedent for widening the matcher, which strengthens the P124 fix recommendation, though note that even 0.18.6's list does not include `SendMessage`, so the resume gap plausibly survives it.

- **Two reviewers converging independently is the strongest signal this stack produces, and it means stop, not iterate.** On 2026-08-23 the architect and the JTBD reviewer, given different prompts and reading different corpora, independently killed the same drafted `.github/dependabot.yml`: the architect on the ground that it reinstated a bot authoring path whose acceptance died with a supersession, the JTBD reviewer on the ground that it routed a code-quality judgement to a persona whose file explicitly excludes it. Neither had seen the other's verdict. When that happens the answer is not a better version of the artefact, it is that the artefact is the wrong shape. Dropping it and recording the open question took one round; arguing with either reviewer alone would have taken several and landed the same place. Third observation of this pattern, after the 2026-08-09 P109 iteration and the 2026-08-23 P141 iteration.

- **Closing a contract-vs-implementation drift puts the same drift in the documents you are editing to close it.** On 2026-08-23 the P140 fix taught the newsletter structural lint that sibling artefacts are named for the publication date, not the phase. The architect's first round then found the script's own usage header still describing the derivation that had just been replaced, and the architect and the risk scorer independently flagged that the skill's copyable invocation block still named the finalise-only path, which would have left the newly-live prep checks uninvoked by the very step that is supposed to run them. Both are the bug being fixed, one layer up: prose that describes a mechanism goes stale the moment the mechanism moves, and a copyable command block is prose. When you close a drift, grep every surface that describes the thing you just changed before you call it done. The reviewers will find them if you do not, but each round costs one.
