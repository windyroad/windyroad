## What Will Surprise You

> Older entries rotated to [`what-will-surprise-you-archive.md`](what-will-surprise-you-archive.md) on 2026-08-08 and again on 2026-08-09 (Tier 3 budget; the 2026-08-09 pass took the trim-noise branch, moving three entries that scored -2 in that retro's signal-vs-noise pass).

- **A plain `mv` onto an existing directory does not refuse, and a scoped `git add -A` after a move aborts on a never-tracked source.** Both surfaced fixing P118 and both exit in ways that read like success or like an ordinary error. `mv a/<date>/ b/<date>/` where `b/<date>/` exists nests to `b/<date>/<date>/` and exits 0, so a publish step reports success while the edition falls out of the one-level-deep edition-count glob. And `git add -A <src> <dst>` after the move exits 128 with `fatal: pathspec ... did not match any files` when the source was never tracked, because the pathspec matches nothing in worktree or index; both pathspecs share one invocation, so the whole command fails after `mv` already landed, leaving the edition promoted with nothing staged. Staging the source BEFORE the move fixes it. The general lesson: reach for `test ! -e <dest>` before any scripted directory move, and reproduce each branch in a scratch repo rather than reasoning about git's pathspec rules.

- **Writing to an ADR makes the compendium hook re-derive that whole entry from the body, so hand annotations on it are transient.** Editing one paragraph of ADR-007 on 2026-08-09 caused `architect-compendium-update-entry.sh` to rewrite the entire ADR-007 block in `docs/decisions/README.md`: the `Chosen` and `Confirmation` lines were replaced with freshly derived text and a `Related:` line appeared. It was a net win that time, because the two lines it replaced were stale threshold restatements P128 had inventoried and the derived replacement says the figures are point-in-time. Do not read that as safe. The two hand annotations `fea3cec` had added to that entry are simply gone, and nothing warned. Three practical consequences. Never hand-annotate a compendium entry expecting it to survive; put the annotation in the ADR body, which is what the hook derives from. Expect `docs/decisions/README.md` in your staged diff whenever you touch an ADR, even a one-line pointer edit, and read that diff rather than staging it blind. And the entry it writes carries an em-dash in the heading, so `no-em-dash-bash.sh` blocks your next Bash call until you rewrite it to a hyphen. Note that this extends P087's scope rather than restating it: that ticket names the retired full-file generator, and the entry hook is a second emitter of the same defect. What the hook does NOT do is recompute `Total ADRs` or either section preamble, which is P135.

- **The session-start `git status` snapshot strips the leading space from the FIRST line only, so line 1 reads as a staged file when it is not.** Porcelain uses two columns, index then worktree, so an unstaged modification is ` M path` with a leading space. In the snapshot handed to a session the first entry loses that space and renders as `M path`, which is the staged form. On 2026-08-09 the risk scorer read `M output/pdf/paper.pdf` off that snapshot, concluded Tom's in-flight paper was staged, and returned STOP on a precondition that was never breached; the file had never been staged and nothing needed unstaging. It cost a full re-score round trip. Never infer staging from the snapshot. Run `git diff --cached --name-only` (or `git status --porcelain <path> | cat -A`, where the leading space is visible as a real byte) and hand that output to any agent you ask to check staging, because a read-only subagent cannot see the index at all and will otherwise reason from the same corrupted line.

- **The commit-message external-comms gate is a DIFFERENT trap from the `--body-file` one above, and the recipe lives in the plugin's briefing, not this repo's.** The gate parses the raw command string with a first-match-wins loop over `-m` and captures only the FIRST one, while the reviewer subagent hashes whatever you wrapped in `<draft>`. So a multi-`-m` commit reviewed as a full body produces two different keys and re-blocks after a genuine PASS, with a message telling you to run the review you just ran. Three recipes work: a single `-m` inlining the whole message reviewed as full text; a multi-`-m` commit reviewed as the SUBJECT LINE ONLY; or `git commit -F <file>`, which sidesteps the gate entirely because it arms only on `-m`/`--message`. The `-F` form is cleanest for anything multi-paragraph. Read `~/.claude/plugins/marketplaces/windyroad/docs/briefing/external-comms-commit-msg-gate.md` BEFORE composing a long commit message; it has been re-hit six-plus times and hitting it again costs a full round trip.

- **The external-comms gate cannot see a body passed with `--body-file`, and the block it emits is then unclearable.** The PreToolUse gate scrapes the draft out of the command string itself, matching a heredoc, then `--body "..."`, then `-m "..."`. With `--body-file /tmp/x.md` nothing matches, so it hashes an EMPTY draft: `sha256("" + "\n" + surface)`. The reviewer subagent hashes the real body from its `<draft>` block, the two keys never meet, and the gate re-blocks after a genuine PASS with the same message telling you to do the review you just did. Nothing in the message hints at the cause. The fix is to pass the body inline as `--body "$(cat <<'EOF' ... EOF)"`, which the gate parses first and by design. Two other traps sit next to this one: the reviewer must be dispatched SYNCHRONOUSLY (a background agent never fires its PostToolUse mark hook), and its prompt must literally start with a `SURFACE: <name>` line and wrap the body in `<draft>...</draft>` markers, or the key is never derived at all. A review run without that shape is wasted work, however good the review is. Observed 2026-08-08 filing agent-plugins#413.

- **Nine problem tickets carry `**JTBD**` / `**Persona**` header lines, and every populated one names an artefact this repo does not have.** P088, P096, P097 and P098 say `**Persona**: plugin-developer` with `JTBD-006` or `JTBD-007`; P124 says `developer` with `JTBD-001`. This repo has no `plugin-developer` persona and no JTBD-006 or 007, and its JTBD-001 is Awareness, an Engineering Leader consulting job retired by ADR-041 on 2026-07-10. The values are the upstream `agent-plugins` corpus leaking in, the same collision class as bare `ADR-NNN`. P125 found this for itself on 2026-08-08 and rewrote its own two lines to say so; the other five were not touched. Two consequences. A ticket's header anchoring is not evidence of anything until you have opened `docs/jtbd/` and confirmed the ID exists here. And the local convention is genuinely no header lines at all: the majority of tickets, including every one captured recently, carry Status / Reported / Priority / Origin / Effort / WSJF and record anchoring in prose under `## Related`. A capture that adds the header lines is diverging from the corpus, not conforming to it.
