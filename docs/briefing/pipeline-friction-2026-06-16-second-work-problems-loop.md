## Pipeline friction (2026-06-16 second work-problems loop)

- **dry-aged-deps deadlocks on exact-pinned deps.** When an exact-pinned dependency (e.g. "playwright": "1.59.1", "react": "19.2.6") crosses its dry-aged age threshold, `dry-aged-deps --check` flags it but `--update --yes` is a no-op (the exact pin caps the range below the mature target), so push:watch loops on "stale deps found". Resolution per P026: manually `npm install --save-exact <pkg>@<target>`, then `rm -f package.json.backup` (the --update attempt leaves a stray backup). Happened twice in one session (playwright, then react/react-dom). Captured as P095.
- **The external-comms marker-hash mismatch (P085) is cross-surface, not commit-message-specific.** It reproduced this session on both git-commit-message AND gh-issue-create, each after both external-comms reviewers returned PASS. Workaround: pre-set the gate markers by running the reviewers on the EXACT final text before the action; if it still blocks, BYPASS_RISK_GATE=1 is the documented override for twice-reviewed-clean content. Evidence appended to P085.
- **push:watch re-scores pipeline risk on every iter's push.** Each AFK iter commits after the orchestrator's last risk score, so the next push:watch blocks on "Pipeline state drift" and needs a fresh wr-risk-scorer:pipeline delegation before draining. Expected (not a bug), but budget one scorer round-trip per iter when running an AFK loop.
- **The external-comms commit-message gate hashes ONLY the first `-m` (the subject line), not the full body.** When you give `wr-risk-scorer:external-comms` the FULL subject+body wrapped in `<draft>`, the marker key it writes will NOT match the key the PreToolUse gate computes for a multi-`-m` `git commit` (the gate's regex `(?:-m|--message)[= ]"([^"]*)"` captures only the first match = the subject), so the commit denies-after-PASS. Fix: review the FULL message once (catches any body leaks), then run a second `wr-risk-scorer:external-comms` pass with `<draft>` = the SUBJECT LINE ONLY so the marker key matches what the gate hashes, then commit `-m "<subject>" -m "<body>"`. Alternatively put the whole message in a single `-m` (the gate then captures the full text). Mechanism confirmed by reading `packages/risk-scorer/hooks/external-comms-gate.sh` lines 235-246 + `lib/external-comms-key.sh`. Observed on P072 commit 4a3602c (2026-06-17); sibling to the P085 marker-hash discard loop but a distinct root cause (first-`-m`-only capture, not working-tree discard).
- **The I13 RFC-trace gate fires when closing a doc-class fix, but the RFC tier is unadopted in this consumer repo.** When working a Known Error fix, manage-problem runs `wr-itil-check-fix-rfc-trace`, which directs auto-creating a problem-traced RFC via capture-rfc. This consumer repo has no `docs/rfcs/` (the ADR-060 RFC/story tier is not adopted here), so honouring that directive would mean bootstrapping the entire RFC-tier infrastructure for an Effort-S doc edit. For a doc-class fix whose design already lives in a confirmed ADR (P070 closed against ADR-032 this way), close the ticket directly with the ADR as the fix-design trace and record the gate decision in the ticket Resolution; do not bootstrap the RFC tier. Observed closing P070 (2026-06-16): the predicate returned `no-rfc-trace: P070` and capture-rfc's ID compute showed `docs/rfcs/ does not exist`.
